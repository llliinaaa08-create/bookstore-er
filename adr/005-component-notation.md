# ADR-005

## Контекст
Для v1.0 онлайн-магазину книг треба розкласти систему на модулі так, щоб фронтенд не ліз у базу напряму, вся бізнес-логіка (знижки, фіксація ціни, перевірка покупки) сиділа в одному місці, а робота з картками лишалася на стороні платіжки

## Рішення
- **5 шарів:** розбила систему на `UI` -> `API Gateway` -> `Service Layer` (4 сервіси) -> `Data Access` (4 репозиторії) -> `Database` (7 таблиць у 3NF). Кожен шар спілкується тільки з сусіднім
- **Нотація ball-and-socket:** взяла стандартні UML-інтерфейси (`provided` і `required`), щоб на схемі було одразу видно, хто які методи віддає і які репозиторії потрібні кожному сервісу 
- **Межа системи:** за рамки v1.0 винесла тільки покупця та `Payment Gateway` (через `IPaymentGateway`), щоб не зберігати дані карток у себе (`NFR-2`)

## Наслідки
- Зміни в структурі таблиць БД зачеплять лише репозиторії, а не API чи фронтенд
- У v2.0 можна спокійно докинути нові фічі (email-розсилки або автоматичний refund з `REQ-6`) як окремі сервіси, не перемальовуючи ядро
